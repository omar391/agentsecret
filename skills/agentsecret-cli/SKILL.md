# AgentSecret CLI

Use the standalone Node CLI as a subprocess. Pass an argument array to the process API; do not build a shell command string. Parse only its documented JSON stdout. The CLI is a separate Node process for canonical Bun applications; importing an SDK or adding a consumer adapter is unnecessary.

For a short reference lookup, a Node application can invoke the packaged module directly:

```js
import { spawnSync } from "node:child_process";
import { createRequire } from "node:module";

const require = createRequire(import.meta.url);
const cliPath = require.resolve("agentsecret/dist/cli.mjs");

const result = spawnSync(
  process.execPath,
  [cliPath, "secrets", "find", "--alias", "DEPLOY_TOKEN"],
  { encoding: "utf8", stdio: ["ignore", "pipe", "pipe"] },
);
if (result.error || result.status !== 0)
  throw new Error("AgentSecret reference lookup failed.");
const receipt = JSON.parse(result.stdout);
if (receipt.status !== "available" || typeof receipt.reference !== "string")
  throw new Error("AgentSecret returned an invalid reference receipt.");
```

Resolve the alias and permission in AgentSecret before invoking the process. The example reads no credential value. For cancellation or longer operations use `spawn` and forward an abort signal; preserve the same argument-array and safe-result contract.

The package also includes direct-invocation examples under `skills/agentsecret-cli/examples/`: `node-find-reference.mjs` for a Node application and `bun-optional-find.ts` for a canonical Bun application that keeps the Node companion as a subprocess. Both use argument arrays and call `agentsecret ensure` before lookup; headless callers receive `{ "status": "setup_needed" }`, `{ "status": "not_ready", "reason": ... }`, or `{ "status": "invalid_local_session" }` when applicable, before any lookup. They emit only safe references, `optional_not_found`, or explicit readiness states. The Node example requires `AGENTSECRET_ALIAS`; set `AGENTSECRET_OPTIONAL=1` to map only a strict not-found result to `optional_not_found`. `node-body-placeholder-request.mjs` demonstrates the currently supported brokered HTTP path: it assumes the owner selected the body-placeholder sink for the alias, sends only the marker through structured stdin, relies on the broker to enforce the alias's approved HTTPS host and `POST` method, and returns only the upstream status code. Its URL must not contain a query string or credentials because the CLI receives the URL as an argument. It does not execute a local host tool or provide Git/binary transport.

`node-owner-private-ensure.mjs` demonstrates a Node consumer calling `secrets ensure` with an exact owner-pinned reference. It emits only `owner_input_required` or `outcome_unknown` with a request ID, or `unchanged`/`updated` with the safe reference. The owner enters any value in the authenticated dashboard; the application never receives it. Retry an unknown result with the same alias and reference so the CLI reuses its saved operation ID.

`bun-owner-private-ensure.ts` provides the same safe status contract for a canonical Bun application and launches the packaged CLI in a separate Node companion process. The Bun application receives only the request ID or verified reference and never a credential value.

## Setup and authority

- Ask the owner to connect the provider and bind a reference to an alias in the dashboard. Provider connection, alias policy and destination permissions are separate.
- Authenticate with `agentsecret login --server <HTTPS-origin>`; use `--device` for device approval and `--write` only when the owner approved write access. Discover approved aliases and destination/method policy with `agentsecret secrets list` or MCP `list_available_secrets`.
- `agentsecret ensure [--server <HTTPS-origin>]` uses the existing session, completes interactive login/device approval when needed, or uses configured CI federation, then checks remote acceptance. Headless callers without a session or workload identity receive `setup_needed` and a nonzero exit. Success confirms session validity only; it does not verify alias bindings or current policy usability.
- `agentsecret status` reports whether local session metadata is missing, stored, expired, or malformed. By default this is an offline check; `agentsecret status --remote` sends a DPoP-authenticated, read-only request to verify that the broker still accepts the agent session. A successful remote check confirms session validity only; it does not verify alias bindings or current policy usability. Output omits the access token, tenant ID, scopes, and policy details.
- `agentsecret logout` removes local session metadata and its signing key. Add `--remote` while the session is still available to first revoke this agent session with a DPoP-authenticated request; local state is cleared even if the server cannot be reached, and the command reports that remote outcome with a failing exit code. If another login replaces the local session during the request, the replacement is preserved. Remote revocation affects only the session used for the request.

## Supported operations

- `agentsecret secrets list` returns only permitted aliases and their allowed destination domains, methods, and owner-selected `credential_sink`. A body-placeholder sink includes the exact `{{AGENTSECRET_SECRET}}` marker the caller must put in a supported request body; other sinks name the header/query placement or broker-handled bearer/basic mode. It also reports `connection_status` and, when the policy still matches its current connection revision, the provider mode and `provider_capabilities` (`read`, `create`, `update`, `conditional_update`, `verify_after_write`, `delete`, and a static safe `reason`). These describe the adapter, not the alias authorization. An unbound legacy policy or unavailable/changed connection has no provider capability claim. When the authenticated grant includes `secrets:write` (or the owner is using the admin session), an alias may also include `owner_write_grant` booleans for create/update/delete; those describe the owner's per-alias grant only. The CLI omits them for agents without write scope. The output omits vault metadata and secret values.
- `agentsecret secrets find --alias <alias> [--store <store>] [--reference <exact-ref> | --binding <JSON> [--inputs <JSON>] | --title <owner-pinned-title> | --login-lookup <JSON>] [--optional]` checks only the alias's owner-bound reference. `--binding` accepts the audited direct shape `{"secret_ref":{"type":"secret_ref","store":"bitwarden-secrets-manager","object_id":"<UUID>"}}` or named-input shape `{"secret_ref_input":"databaseCredential"}` with `--inputs '{"databaseCredential":{"type":"secret_ref","store":"bitwarden-secrets-manager","object_id":"<UUID>"}}'`. A named-secret locator uses `{"secret_locator":{"kind":"named_secret","store":"onepassword-connect","name":"<owner-pinned-title>"}}`; its named-input form uses `{"secret_locator_input":"databaseCredential"}` with `--inputs` containing only that named locator. A login lookup locator supplies only the owner-pinned username and URI set; its named-input form uses the same `secret_locator_input` wrapper. The broker supplies the owner-pinned title and field ID, and rejects non-empty JSON Pointer field paths because the Connect mapping is not defined. Each input map contains only the selected typed value, and the CLI sends only that selected ref or locator to MCP. Specify `bitwarden-secrets-manager` explicitly because the manager defaults an omitted store to `bitwarden-cli`; the binding type may be omitted. The BWS UUID must exactly match the alias's owner-bound BWS reference and BWS field paths are refused. For Connect, a direct or named-input object/field ref maps only the exact JSON Pointer /fields/<field-id>/value to its canonical owner-bound reference; percent-encoded field IDs and missing, malformed or mismatched paths fail before provider lookup. `--store` optionally asserts the alias's current provider binding (`bitwarden-cli`, `bitwarden-secrets-manager`, `onepassword-connect`, `onepassword-service-account`, or `lastpass`). A mismatched binding fails before provider lookup, and a mode without a matching configured connection fails as unavailable. `bitwarden-cli` means Bitwarden Password Manager, never BWS or Connect; the current `bitwarden` connection is BWS, so the two cannot be interchanged. A title or structured login selector must match the alias policy exactly; arbitrary title, username, or URL search is refused. The `login_lookup` JSON contains the owner-pinned `title`, `username`, exact `uris`, `fieldId`, and optional exact `fieldPath`. It queries by exact title, then verifies the selected Connect item and returns only the alias-bound reference. Parse `{status, provider, reference}`. With `--optional`, only `secret_not_found` and `secret_field_not_found` become `{status:"optional_not_found"}`; ambiguous, denied, and malformed responses still fail. It does not return a value or enumerate a vault. Companion-gated stores (`bitwarden-cli`, `onepassword-service-account`, `lastpass`) have no cloud adapter and fail as `secret_store_unavailable` before lookup; BWS name/login locators fail as `secret_binding_unsupported` before lookup. `env_var` locators are recognized only to reject them as `local_only_env_var` before broker/provider access and are never resolved by the cloud.
- `agentsecret secrets save --alias <alias> --title <title>` and `agentsecret secrets update --alias <alias> --reference <exact-ref>` require an interactive terminal. The value is entered at a hidden prompt. Never add `--value`, redirect stderr, pipe a value, or put a value in a process argument. Connect writes use the broker path. A 1Password service-account write sends no value to the Worker; after cloud authorization the enrolled local companion runs the SDK, verifies readback, and returns only a safe reference/status receipt. A timeout may leave an unknown outcome: rerun the same command with the same target and value to reconcile its receipt; do not use `--new-operation` until provider state has been checked.
- `agentsecret secrets ensure --alias <alias> --reference <exact-ref>` requests private owner input for an exact owner-pinned reference. For Connect, the owner enters the value in the authenticated dashboard. For a 1Password service-account request, enter it only at the local companion prompt or complete the existing dashboard request with `agentsecret secrets fulfill --request-id <id>`. The CLI sends only the alias, reference, intent, and a persisted operation ID; comparison and any update happen inside the trusted owner path. It reports `owner_input_required` with a request ID while waiting, then `unchanged` or `updated` with a verified safe reference. Repeating the command reuses the same operation ID while the outcome is pending or unknown. This is owner-mediated ensure, not managed-runtime capture or compare.
- `agentsecret secrets delete --alias <alias> --reference <exact-ref>` deletes only the policy’s owner-pinned field and requires a separate owner delete grant plus an interactive terminal. Confirm by typing the full reference when prompted. Connect deletion uses the broker path. A 1Password service-account delete is completed locally after executor-bound admission. The request carries no value. On an unknown result, reconcile the same alias and reference before starting another operation.
- `agentsecret secrets fulfill --request-id <id>` completes an existing service-account create, update, ensure, or delete request from the dashboard. Run it under the same agent session that created the request; another agent cannot claim that ticket. It never creates a second ticket. Writes and ensures prompt for the value privately; deletes require the exact reference confirmation. Public service-account write flags remain disabled pending live provider acceptance.
- `agentsecret request --alias <alias> --url <HTTPS-url> [--method POST] [--data <JSON> | --stdin]` makes a policy-bound HTTPS request through the broker. `--data` is JSON supplied as an argument and keeps its exact text as the request body. For caller headers or to keep request content out of process arguments, pass one UTF-8 JSON object to `--stdin`, shaped as `{ "headers": { "If-Match": "\"version\"" }, "body": "{\"key\":\"value\"}" }`; only `headers` and a text `body` are accepted. The body string is sent exactly as provided, avoiding JSON number/format changes from parsing and reserialization. If a text body has no `Content-Type`, the CLI sets `text/plain;charset=UTF-8`; set a content type such as `application/json` explicitly when needed. Stdin is limited to 48 KiB and the serialized broker request to 60 KiB, with at most 32 headers, 80-byte token names and 4 KiB ASCII values. The CLI rejects duplicate names (case-insensitively), credential, cookie, host, proxy, forwarding, hop-by-hop, and broker-controlled encoding headers before contacting the broker. The broker revalidates headers and binds the exact normalized request to its one-use capability. This supports bounded text/JSON HTTP only; binary bodies, streaming, caller-selected compression, redirects and custom TLS trust are unavailable. Use only the approved destination and method, parse the bounded response, and do not treat this as a general-purpose local CLI or arbitrary binary/Git transport.
- If the owner selected `body_placeholder` for the alias, put exactly one `{{AGENTSECRET_SECRET}}` marker in the request body; the caller sends only this marker, and the authorized broker substitutes the selected vault value after capability redemption. For `application/json` or `+json`, the marker must be a whole JSON string value or a JSON value slot, not a key or substring; the broker preserves the rest of the caller's JSON text and escapes the secret for that position. `text/plain` uses literal substitution. Other media types and malformed JSON templates fail before outbound dispatch. The marker is only enabled by the owner's alias policy and the destination/method are still checked normally.
- `agentsecret mcp --server <origin>` starts the authenticated stdio bridge. Use the advertised tools and their schemas. MCP `secrets_save` requests private owner fulfillment for create, exact-reference update, or ensure; the agent must not supply a secret value. Ensure is available only for an exact owner-pinned reference with the existing update grant. The owner enters the value in the authenticated dashboard, and the agent receives only a retained request ID, safe reference, and unchanged/updated status; a local service-account retry uses that ID to recheck its value against the original payload binding without redispatching a write.

## Unavailable operations

`agentsecret run` is disabled pending native macOS runtime qualification and strict credential mediation. Do not claim support for managed-runtime browser login/fill, capture/store, TOTP, managed-runtime compare/ensure, arbitrary host tools, Git credential helpers, or provider modes whose capability reports require a companion. A cloud MCP tool does not run a local browser or local command. Use the migration matrix in [references/consumer-migration.md](references/consumer-migration.md) to distinguish today's callable behavior from the target behavior and adoption work.

There is no raw secret-resolution command. If an application currently expects a plaintext string from a resolver, change its call site to ask AgentSecret to perform the intended secret-consuming operation inside a qualified managed runtime. Renaming the binary or swapping an import cannot preserve that value-returning behavior under the no-export contract. Do not silently migrate consumers, copy vault enrollment, or delete local profile/vault data.
