## Qualification boundary

The audited snapshot SHAs and branch-search limits are recorded in [ARCHITECTURE.md](../../../ARCHITECTURE.md#cueintent-secret-manager-replacement). The source audit searched committed HEADs and registered worktree commits; uncommitted files and installed-runtime behavior were not audited. Dependency declarations alone do not prove a secret-use call path.

The reviewed manager source defines four structured binding forms: `secret_ref` contains a ref; `secret_ref_input` names an input containing a ref and permits the legacy `field_path` override; `secret_locator` contains a `login_lookup`, `named_secret` or `env_var` locator; and `secret_locator_input` names an input containing one of those locators. Refs and login/name locators default to the `bitwarden-cli` store; `env_var` has only a local variable name. AgentSecret accepts direct and named-input `secret_ref` bindings for an exact owner-bound Bitwarden Secrets Manager UUID, with no field path. It accepts direct and named-input `named_secret` and `login_lookup` locators only for owner-pinned 1Password Connect records. `login_lookup` accepts only the pinned username and URI set; the broker supplies the owner-pinned title and field ID. Non-empty JSON Pointer field paths remain refused for named_secret and login_lookup locators. Structured Connect secret_ref bindings map only the exact /fields/<field-id>/value JSON Pointer to a canonical owner-bound item#field reference, and percent-encoded field IDs are rejected. Locator inputs contain only the selected typed locator, and policy matching and exact bound-reference verification still apply. For `secret_ref_input`, `--inputs` must contain only the named typed ref, and the CLI forwards only that selected ref to MCP. BWP refs remain unavailable until a distinct connection exists. For Connect secret_ref bindings, the field ID is derived only from the exact /fields/<field-id>/value JSON Pointer; the resulting reference must equal the owner-pinned Connect reference. Companion-gated stores (`bitwarden-cli`, `onepassword-service-account`, `lastpass`) have no cloud adapter and fail as `secret_store_unavailable` before lookup; BWS name/login locators fail as `secret_binding_unsupported` before lookup. `env_var` is recognized only to reject it locally and cloud-side as `local_only_env_var` before broker/provider access; it is never resolved by the cloud. `secrets find --store <store>` is only an optional assertion that the alias's existing owner binding uses that provider mode; mismatch is rejected before provider lookup. Its accepted values are `bitwarden-cli`, `bitwarden-secrets-manager`, `onepassword-connect`, `onepassword-service-account`, and `lastpass`. A mode without a matching configured connection fails as unavailable. The existing `bitwarden` connection means Bitwarden Secrets Manager; the distinct Bitwarden Password Manager mode cannot fall through to it. BWS structured refs still require UUID equality. Connect structured refs map an item ID and exact /fields/<field-id>/value JSON Pointer to an owner-bound reference, with policy equality checked before provider lookup. Other stores and unresolved or cross-account mappings remain unsupported; local `env_var` use requires an explicitly permitted trusted runtime and cannot upload the host value.

Today, MCP `secrets_find` and CLI `secrets find` share a reference-only operation; CLI `--optional` maps only strict explicit not-found results to `optional_not_found`. Connect lookup accepts an owner-pinned title or structured login locator containing exact title, username, URI set and field ID; it does not provide generic vault search. Owners can configure that locator when creating a policy or revise/clear it later without replacing the other policy fields. Updating a policy binding requires existing agents to obtain fresh owner consent. `secrets list` reports permitted aliases, domains, methods, connection status, current provider capabilities, and the owner-selected `credential_sink` for each authorized alias. The sink names a header or query parameter, identifies the exact body marker, or reports broker-handled bearer/basic placement; it discloses no credential value. Per-alias owner write grants are visible only to write/admin-scoped callers. Provider capabilities describe adapter support and never imply alias authorization. For HTTP `request`, an owner may select one `{{AGENTSECRET_SECRET}}` body placeholder; JSON string/value slots and `text/plain` are substituted after one-use capability redemption, and the packaged federated CLI path has synthetic acceptance for response redaction. This does not connect arbitrary guest processes to the broker or establish runtime egress enforcement. MCP `secrets_save`, dashboard fulfillment, CLI Connect save/update, and CLI owner-private ensure are distinct surfaces with different input paths. Packaged Node and Bun examples demonstrate direct subprocess invocation; the Node HTTP example has extracted-package acceptance through the real local Worker and synthetic upstream, checks the selected sink and destination policy, and emits only the upstream status. These examples do not certify consumer migration or runtime parity. The shared production-ready parity claim across MCP, direct CLI, dashboard, provider modes and protected runtime is still open. Synthetic tests do not certify live providers, hosts or consumers. The remaining acceptance cases are tracked by the maintainers. MCP `secrets_find` also accepts direct and named-input structured BWS UUID `secret_ref` bindings, direct and named-input Connect `secret_ref` object/field bindings, owner-pinned Connect `named_secret` and `login_lookup` locators, and audited `env_var` locators that fail closed as `local_only_env_var`; companion-gated stores fail as `secret_store_unavailable` and BWS locators as `secret_binding_unsupported` before provider access. `secrets_save` and `secrets_delete` reject malformed argument shapes, unsafe Unicode, and extra keys before authorization or provider dispatch; `secrets_find` rejects malformed bindings, locators, and conflicting argument combinations before provider access. MCP JSON-RPC envelopes reject invalid JSON, array roots, wrong versions, non-string/boolean IDs, array params, unsupported protocol versions, and unknown methods before dispatch. These boundaries are synthetic-tested only; consumer migration, live providers, hosts, and runtime parity remain open.
